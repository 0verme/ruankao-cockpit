> **阶段**：Research / Audit（不进入开发、不进入最终计划）
> **审计日期**：2026-09-20（UTC+8）
> **审计范围**：10 个 GitHub 仓库（4 个指定 + 6 个扩展）、1 份第三方 30 天指南（OCR 全文）、1 份官方大纲/教材结论
> **取证方式**：全仓库浅克隆 + 目录树遍历 + 代码/JSON/CSV/Markdown 逐文件阅读 + 无文本层 PDF 的 300–400 DPI OCR + GitHub API（metadata / issues）

## Executive Summary

### 结论一：内容已经足够，不需要从零整理教材

【事实】现行官方教材仍是 **《系统架构设计师教程》叶宏主编，第 2 版，清华大学出版社 2022.11**（CIP 数据 "—2版"，ISBN `978-7-302-61992-5`）。已在仓库中确认到 20 章、721 页的完整 Markdown 化版本，并且该仓库对教材做了逐页（708 页）核对与图表资产登记。

【事实】2016 下半年 – 2025 下半年的三科试卷已被完整整理为 Markdown，并带有机器可读清单（36 份试卷 × 完整性 / 答案可信度 / 同名冲突标记）。

【推断】本项目**唯一必须自己生产的"知识内容"是三样东西**：taxonomy 归一化层、案例能力/采分点表、论文个人项目素材。其余全部应走"引用 / 索引"路线。

### 结论二：Star 数与可复用性几乎无关，甚至负相关

【事实】`xxlllq/system_architect` 有 **8,803 star**，但整个仓库的可复用结构化内容只有 2 份机考操作 PDF；其余 7 个 `.txt` 全部指向付费站点 `fchxxn.com/exam` 与阿里云盘链接。

【事实】`YoungHong1992/ruankao-senior-architecture-designer` 只有 **48 star**，却提供了教材全文 Markdown + 大纲 Markdown + 36 份真题 + 4 个审计 JSON + 质量门禁 CI。

【推断】选源标准应是"仓库里有没有可机读的正文与元数据"，而不是 star 数。

### 结论三：四个仓库恰好覆盖工作台的四个不同层

【事实+推断】

| 层 | 最佳来源 | 为什么 |
|---|---|---|
| 权威 taxonomy 锚点 | `YoungHong1992/...`（官方大纲 + 教材章节） | 唯一按官方大纲/教材章节结构落地为 Markdown 的仓库 |
| 题库 + 掌握度数据模型 | `Zhang-986/ruankao-architect-practice`（`data/bank.json` + `src/core.mjs`） | 唯一带确定性复习算法（1/3/7/15 天）与诊断导出的实现 |
| 案例 / 论文方法论与素材骨架 | `wujiaming88/awesome-ruankao` | 唯一把"项目素材 → 适用论题 → 论述提纲"和"能力 → 采分点 → 易错点"写成结构化文档的仓库 |
| 每日任务与学情状态的最小先例 | `Nye-2/archprep`（CSV 学情 + 记忆卡片 + 课次计划） | 唯一把"课次 / 达标标准 / 掌握度 / 下次复习"落成表格的仓库 |

【推断】没有任何单一仓库同时具备"内容 + 题库 + 进度引擎 + 计划器"。这正是本项目存在的理由，也是唯一需要自建的部分。

### 结论四：版权上不存在"可以整包复制"的来源

【事实】授权的四种状态在本次审计中全部出现：无授权（`xxlllq`、`Nye-2`、`longyi-xw`）、MIT 但内容为第三方（`sobermh`、`xiaomabenten`、`ruankaodaren`）、CC BY-SA 4.0（`wujiaming88`）、显式"非统一授权"（`YoungHong1992`）。

【推断】若本项目公开到 GitHub：**代码可以 MIT，题库与正文不可以随仓库分发**。安全形态是 `content index + 本地导入`，见第七节。

### 结论五：现有 30 天计划全部是"静态模板"，且都有同一个结构性缺陷

【事实】`xiaomabenten` 中的《系统架构设计师考前 30 天冲刺学习指南》与《60 天软考上岸计划》是同源模板：**案例分析板块逐字相同，论文练习同样被压到"考前 17–19 天"**。30 天版把论文练习放在第 21–24 天（5/15–5/17），仅 3 天、每天 1 篇。

【事实】`Altria1979` 的 2023 备考日志显示论文复习集中在最后 4 天，且其案例分析以 36 分未通过，自述原因是"大数据知识点没有复习到"。

【推断】这正是"30-Day Backbone + Rolling 7-Day + Daily Adaptive"必须取代固定日程的直接证据：模板无法处理(1)复习欠债、(2)弱项暴露、(3)断续学习。

### 5.2 从证据中得出的七条结论

1. **哪些内容应固定在 Day 1–30？**
   【推断】三类：(a) 质量属性 + 架构风格主轴（三科共用，见 4.1）；(b) 每日复习/错题（所有计划都以"错题巩固"形式重复出现）；(c) 论文素材积累（每天 1 张素材卡），**但不等于每天写全文**。证据：`wujiaming88` 12 周路线把"搭建 2 个可复用项目背景"放在第 3–5 周，而不是最后。

2. **哪些内容应动态变化？**
   【推断】真题套卷的选择、章节知识点的题量配比、案例能力专项的顺序。证据：可用真题有 36 份（`YoungHong1992`）而 30 天最多消化 ~15 份 → 必须按弱项选卷；希赛 30 天硬性从 2016下 顺序推到 2024下，是"模板驱动"而非"弱项驱动"。

3. **哪些任务必须每天重复？**
   【推断】复习到期卡片 + 错题回访 + 论文素材卡 1 张。证据：`Zhang-986` 的 `memoryIntervalDays()` 会产生**每日到期集合**（1/3/7/15），不复访就会累积欠债；`Nye-2` 的执行协议要求每课沉淀 1–3 张卡片。

4. **哪些应根据弱项重新分配？**
   【推断】案例能力专项（如"缓存""质量属性场景"）、以及低正确率知识域的题量。证据：`Zhang-986` `summarizeAttempts()` 已实现 `weakModules(top5)` + `inferWeakModule()`，说明"按弱项重排"在数据上是可算的；`wujiaming88` 要求把错误分为"知识缺失/审题错误/计算错误/表达缺采分点"四类才能重排。

5. **综合 / 案例 / 论文应并行还是分阶段？**
   【推断】**弱并行**：综合 + 案例从第 1 天起并行（案例是小体量高频任务），论文在前期以"素材/提纲"形态并行、中期起进入"全文"形态。证据（反向）：希赛 30 天与 60 天均为完全串行且论文压后 → `Altria1979` 2023 年因该结构落榜（案例 36 分）；正向：`wujiaming88` 12 周在第 6–8 周就进入"三科并进"，并明确"每两周一篇全文"。

6. **30 天是否应完全按天固定？**
   【推断】**不应**。证据：`Altria1979/README_2023.md` 在 22 天里出现 ≥6 个休息日（10/14、10/23、10/26–10/29、11/1），且 10/30 学到凌晨 2 点——真实节奏是**弹性容量**而非日历刚性；希赛打卡表也只能记录"做了多少"而无法重排。

7. **是否更适合 `30-Day Backbone + Rolling 7-Day + Daily Adaptive`？**
   【推断】**是**，且这是本次审计中对"要不要自建计划器"最直接的支持证据：
   - Backbone 负责不可协商的锚点（三科主梁、论文里程碑、套卷时点、机考演练）
   - Rolling 7-Day 负责吸收容量波动与复习欠债（`Zhang-986` 的 due 集合 + `Nye-2` 的"下次复习"字段都是滚动窗口）
   - Daily Adaptive 负责把当天实际结果写回（`attempts` / `掌握度`），并触发下一轮重排
   - 反例证据：所有"固定日表"资料都没有任何重排机制。

### 5.3 关键量化事实（供 Draft 使用）

- 三科均 **75 分 / 合格线 45 分 / 不滚动保留**（`wujiaming88` 学习路线表；`2026下半年备考总指南` 亦确认"单科成绩不滚动保留"）

### 7.3 对本项目公开仓库的合规建议（推断）

1. **正文不入库**：仓库只保存 `content_index`（`title / source_repo / source_path / source_commit / topic_id / license_tag / fetch_hint`），正文由使用者本地导入。
2. **题库不入库**：导入器（importer）随仓库发布，数据文件放 `.gitignore`；文档说明用户须自行获取。
3. **我方原创内容可以开源**：taxonomy、案例能力表（自己总结的枚举与映射）、论文素材模板的**结构**、planner 与 progress engine 代码。
4. **引用 CC BY-SA 4.0 内容时**：必须署名 + 以相同协议共享衍生内容；若不想让整个项目变成 CC BY-SA，则**只能引用指针**。
5. **标注机器可校验的元数据**：每个索引条目带 `license_tag ∈ {MIT, CC-BY-SA-4.0, NONE, PROPRIETARY}`，缺失即默认 `PROPRIETARY`。

## 九、Recommended Source Architecture

```text
【第一层｜权威锚点 · 唯一】
官方考试大纲（第2版, 2022）
        ↓ 产出并冻结
Content Taxonomy（13 类综合 / 9 类案例 / 5 类论文 + 稳定 topic_id）
        ↑ 交叉校验：教材 20 章目录（YoungHong1992）
                   Xisai 权重区间（仅排序用）
                   Zhang-986 module_counts（仅 sanity check）

【第二层｜内容索引 · 只存指针】
GitHub materials（教材/大纲/真题正文）
        ↓ 解析为
Content Index：{topic_id, source_repo, source_path, source_commit, license_tag, fetch_hint}
        ↑ 首选来源：YoungHong1992（结构最稳）
        备用来源：xiaomabenten PDF（无文本层者需 OCR，成本高，列为 fallback）

【第三层｜练习索引 · 只存指针 + 元数据】
Question Sources（wujiaming88 真题/模拟、Zhang-986 bank）
        ↓ 归一化
Practice Index：{question_id, subject, topic_id, capability[], difficulty, source, answer_confidence}
        ↑ 质量门禁：answer_confidence ∈ {official, high, medium, low}；low 不参与掌握度加权

【第四层｜本地私有状态 · 不入库】
Personal State：attempts / case_scores / essay_drafts / my_project_material / study_sessions
        ↑ 存储形态：本地 DB 或 JSON（沿用 Zhang-986 的 export/import schemaVersion 约定）

【第五层｜自产内容 · 可以开源】
1. Taxonomy 归一化表
2. 案例 capability / scoring_point / common_error 枚举表
3. 论文素材模型（结构，非内容）
4. Progress Engine（确定性规则）
5. 30-Day Backbone + Rolling 7-Day 生成器
```
