# 架构视图与软件复用

## 今天学会什么
- 识别三种架构描述框架各自的视图组成。
- 区分机会复用与系统复用，并列举来源中的可复用资产。
- 说明架构风格如何以构件、连接件和约束组织系统。

## 先建立直觉

复杂系统无法靠一张图讲清。视图模型从不同角度描述同一个系统；复用则把已有架构经验、组件或文档用于后续开发。两者解决不同问题：视图帮助沟通结构，复用帮助重复利用已有资产。

## 核心知识

### 架构描述的视角
- **UML 4+1：**用例（场景）、逻辑、进程、实现、物理五个视图。
- **TOGAF：**业务、应用、数据、技术架构。
- **Hofmeister 四视图：**概念、模块、执行、代码视图。
- **CMU-SEI Views and Beyond：**模块视图、构件与连接子视图、分配视图。

同一个系统可使用多种视图框架；本项没有给出三者之间的转换规则，不把名称相似当成一一对应。

### 复用的范围与时机
软件复用可提高开发效率、保证软件质量、降低成本与风险。可复用资产不止代码，还包括架构、通用组件、设计方案及其文档、用户手册、测试计划和测试用例。**机会复用**是在开发中发现可复用资产后使用；**系统复用**则在开发前就规划要复用什么。

架构风格/模式表达特定领域常见的系统组织方式：它定义构件与连接件词汇，以及如何组合它们的约束。复用过程可整理为获取资产、管理资产、使用资产。

## 一张脑图式结构
```text
架构描述 → 选择多个视图角度（UML / TOGAF / Hofmeister / SEI）
软件复用 → 获取资产 → 管理资产 → 使用资产
                         ├─ 机会复用：开发中发现
                         └─ 系统复用：开发前规划
```

## 易混点 / 对比
- 机会复用是“遇到合适资产再用”；系统复用是“事先规划复用”。
- 架构风格不是单独的构件清单，还包含构件、连接件及组合约束。
- **SOURCE_GAP：**原始提纲提出“架构概念”和“三大作用”但未给具体定义；本单元只展开有明确信息支持的视图与复用部分。

## 架构师视角
选择视图时应考虑沟通对象和要回答的问题；选择复用资产时则要关注资产本身、组合约束及可管理性。把架构视图与复用过程分开记录，可避免把“描述系统”误当成“取得并使用资产”。
