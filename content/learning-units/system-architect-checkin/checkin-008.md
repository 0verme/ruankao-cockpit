# ABSD：从架构需求到架构演化

## 今天学会什么
- 说出 ABSD 以架构驱动、从系统逐步细化到构件和类的特点。
- 按架构需求、设计、文档化、复审、实现、演化梳理主要活动。
- 解释质量/商业目标、架构风格与构件识别如何进入开发过程。

## 先建立直觉

ABSD 将架构当作开发的组织中心：先理解用户和系统目标，再形成架构模型，将构件映射进模型，最后实现、组装并在需求变化时演化。它不是一次画完架构图，而是自顶向下、递归细化。

## 核心知识

方法基础包括功能分解、选择架构风格以回应质量和商业需求，以及软件模板的使用。顶层可分成概念子系统与软件模板；下一层继续分为概念构件和附加模板，直到形成构件与类。

开发过程可记为六步：**架构需求**（获取用户需求、识别构件；需求来源包括系统质量目标、系统商业目标及开发人员商业目标）→ **架构设计**（提出模型、映射构件、分析交互、形成架构并评审）→ **架构文档化**（规格说明及质量设计说明）→ **架构复审**（尽早识别风险与缺陷）→ **架构实现**（实现、组装、测试构件）→ **架构演化**（变化分类、制定计划、增删改构件与交互，再组装测试和评审）。

文档面向使用者编写，分发给相关人员，并确保开发者持有最新版本。演化不是只改需求文字，也可能要求同步更新构件关系。

## 一张脑图式结构
```text
目标/需求 → 识别构件 → 架构模型与映射 → 文档/复审
    → 构件实现、组装、测试 → 需求变化时计划并演化
```

## 易混点 / 对比
- 架构设计与架构实现不同：前者建立模型并分析交互，后者实现、组装和测试构件。
- 架构复审关注风险及设计缺陷；不是等系统实现完才做的测试。
- 架构演化包括构件及其相互作用的更新，不只是替换一个模块。

## 架构师视角
架构师需要把需求中的质量与商业目标转换为架构约束，并保持模型、构件、文档和实现之间一致。需求变化时，先分类并制定演化计划，再更新构件及其交互，有助于避免局部改动与全局结构脱节。
