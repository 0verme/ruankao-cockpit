# 架构评估：方法与关键概念

## 今天学会什么
- 区分问卷/检查表、场景和度量三类评估入口（仅在来源明确处展开）。
- 说明敏感点、权衡点、风险点和利益相关者各指什么。
- 用刺激、环境、响应描述一个质量属性场景。

## 先建立直觉

架构评估不是泛泛判断“设计好不好”，而是围绕质量目标收集信息，检查架构决策可能带来的结果。场景把利益相关者与系统交互说具体，度量方法则把属性与可观察度量联系起来。

## 核心知识

### 三种评估入口
- **问卷或检查表：**来源只列出方法名称，没有给出操作步骤或适用条件。
- **基于场景：**来源列出该方法，但未展开方法流程。
- **基于度量：**建立质量属性与度量间的映射原则，从架构文档获取度量信息，再按映射分析推导系统质量属性。

### 评估用语
- **敏感点：**一个或多个构件及关系的特性，其变化会影响某个质量属性。
- **权衡点：**会影响多个质量属性的特性，也可视为多个质量属性的敏感点。
- **风险点：**存在潜在隐患的架构决策。
- **风险承担者/利益相关人：**架构决策影响到利益的人。
- **场景：**从利益相关者角度简述与系统的交互，来源指出通常用刺激、环境、响应表达。

**SOURCE_GAP：**问卷/检查表与场景法的具体步骤、架构评估的重要性，以及质量属性场景六要素的其余说明未在 Prompt 中提供，不补写标准流程。

## 一张脑图式结构
```text
架构评估
├─ 问卷/检查表（方法标题；细节待补证）
├─ 场景（利益相关者：刺激 → 环境 → 响应）
└─ 度量（架构文档信息 + 属性/度量映射 → 推导）
   ├─ 特性变化影响一个属性 → 敏感点
   └─ 特性影响多个属性 → 权衡点
```

## 易混点 / 对比
- 敏感点关注对某一质量属性的影响；权衡点牵涉多个质量属性。
- 风险点是潜在隐患的决策；利益相关者是受决策影响的人。
- 不能把“基于度量”简化成只列性能数字；来源描述了映射、取数、分析三个活动。

## 架构师视角
架构师需要说明决策影响了哪些属性、哪些构件关系是敏感的，以及不同利益相关者是否面临冲突。证据不足时，评估结论应保留不确定性，而不是把 checklist 名称当成已完成评估。
