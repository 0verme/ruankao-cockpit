# 解释器与规则系统

## 今天学会什么
- 概括解释器执行程序时涉及的程序、执行状态和解释引擎。
- 说明规则系统如何用条件—动作规则驱动系统行为。
- 区分知识库、工作内存与规则解释器。

## 先建立直觉

解释器风格把行为描述为“读取规则或指令，再按当前状态执行”；规则系统则把业务逻辑拆成显式条件和动作，由推理引擎决定何时触发。两者都把行为描述与执行机制分开组织。

## 核心知识

### 解释器的组成
被解释的程序使用某种特定语言编写；程序执行状态记录当前执行位置、调用栈和全局变量等；解释器引擎执行“取指令—理解操作—执行底层动作”的循环；解释器自身还维护工作所需的内部状态。程序状态回答“被解释程序运行到哪里”，引擎状态则属于解释器本身。

### 规则系统的组成
业务逻辑/领域知识表达为“如果……那么……”规则，推理引擎匹配并执行规则：
- **知识库：**包含规则集与事实集。
- **工作内存：**保存初始事实、输入事实及规则执行产生或修改的事实，是推理过程的动态状态。
- **规则解释器：**监控工作内存，按规则执行识别—行动循环。

## 一张脑图式结构
```text
规则系统
├─ 知识库：IF-THEN 规则 + 初始事实
├─ 工作内存：输入/推理中动态事实
└─ 规则解释器：观察状态 → 匹配 → 执行动作 → 更新状态
```

## 易混点 / 对比
- 规则集定义可触发的条件—动作关系；工作内存存当前事实与推理状态。
- 被解释程序的执行状态不等于解释器引擎内部状态。

## 架构师视角
当业务规则需要显式表达时，将规则和事实状态与执行循环分开，便于看清行为由哪些规则触发。设计时需明确规则的执行状态从哪里来；具体性能、冲突解决或安全取舍需补充来源后再展开。
