# 软件开发模型与方法（一）

## 今天学会什么

- 用“阶段顺序、反馈方式、风险处理”三个角度区分瀑布、演化、螺旋与 RAD。
- 说明抛弃式原型和演化式原型的目的差异。
- 识别喷泉模型、形式化方法各自强调的过程特征。

## 先建立直觉

开发模型不是项目名称的集合，而是安排工作与反馈的方式。需求稳定时，清晰的阶段交接可能更易管理；需求尚不清楚时，尽早获得用户反馈更有价值；当风险主导项目时，模型需要把风险分析放到迭代中。选模型时要看问题，而不是只背模型的优缺点。

## 核心知识

### 瀑布：阶段交接清楚

瀑布模型把计划、需求分析、设计、编码、测试、运行维护划为有先后关系的阶段，前一阶段输出成为后一阶段输入。阶段边界和文档有利于管理、追溯；代价是需求变化时调整链条较长，早期遗漏可能到后期才显现。来源将其适用情境概括为需求明确、稳定、变化较少的项目。

### 演化 / 原型：让反馈参与需求澄清

先快速做出原型，再根据使用反馈改进，反复演化到目标产品，适合需求暂时无法完整定义的情形。**抛弃式原型**主要探索需求或方案，达到目的后丢弃；**演化式原型**逐步成为最终产品，因此要考虑性能、可靠性、设计和文档。若没有整体规划或变更控制，演化过程可能失去边界。

### 螺旋：按风险组织迭代

每轮围绕目标设定、风险分析、开发与有效性验证、客户评审展开。它以原型式迭代为基础，把风险分析明确纳入过程；因此“有迭代”并不足以识别螺旋模型，风险驱动是关键线索。

### RAD、喷泉与形式化方法

- **RAD**借助构件复用、用户参与的集中研讨和迭代，争取较快得到可工作的系统；速度依赖用户协作和可复用构件条件。
- **喷泉模型**以对象为驱动，强调迭代及阶段间没有明显间隙，不要求把各活动理解为一次性流水线。
- **形式化方法**建立在严格数学基础和精确语义上。来源列举净室软件工程：用盒结构规约建模，以正确性验证发现和排除错误，并用统计测试收集可靠性信息。

## 一张脑图式结构

```text
如何组织开发？
├─ 阶段依次交接 → 瀑布（需求稳定时更合适）
├─ 原型反馈逐步改进 → 演化模型
│  ├─ 探索后丢弃 → 抛弃式
│  └─ 继续演变为产品 → 演化式
├─ 每轮显式分析风险 → 螺旋
├─ 用户协作 + 构件复用求快 → RAD
├─ 对象驱动、迭代且无明显阶段间隙 → 喷泉
└─ 数学语义与规约/验证 → 形式化方法
```

## 易混点 / 对比

| 对比 | 抓手 |
|---|---|
| 瀑布 vs 演化 | 阶段依次交接 vs 原型反馈驱动改进 |
| 抛弃式 vs 演化式原型 | 原型是否继续成为最终产品 |
| 演化 vs 螺旋 | 都可迭代；螺旋显式以风险分析组织每轮 |
| RAD vs 形式化方法 | 一个突出用户参与、复用与速度；另一个突出严格规约与验证 |

## 架构师视角

模型选择会影响需求反馈出现的时间、阶段交付物及风险暴露位置。若需求不稳定却把阶段交接当成不可变输入，后期变更压力会上升；若采用原型演化，也仍需处理结构、版本和质量要求。对来源所述模型而言，关键取舍是反馈灵活性与过程控制，而非“新模型必然优于旧模型”。

## 记忆锚点

- 瀑布看阶段交接，演化看原型反馈，螺旋看显式风险分析。
- 原型是否被保留，是区分抛弃式与演化式原型的抓手。
- RAD 的来源线索是用户参与、研讨、构件复用和较快得到可运行系统。
- 净室条目强调规约、正确性验证与统计测试。
