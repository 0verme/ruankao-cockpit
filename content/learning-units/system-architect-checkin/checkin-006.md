# 基于构件的软件开发

## 今天学会什么

- 解释 CBSD/CBSE 为什么把重点从重复编写转向识别、适配和组装可复用构件。
- 列出来源要求的构件特征和主要开发活动。
- 区分顺序、层次、叠加三种构件组装，以及三类接口兼容问题。

## 先建立直觉

如果已有构件能满足需求的一部分，基于构件的开发会先评估能否复用，再决定如何适配与集成。它不是简单地把现成模块拼起来：构件要有清晰接口、足够文档、能在目标环境部署，还要检查请求接口与提供接口是否匹配。

## 核心知识

### 思路与构件特征

CBSD/CBSE 是一种以复用构件来设计、构造软件系统的方法，把开发重点由程序编写转向已有构件的选择和组装。来源列出的构件特征包括：

1. **可组装：**外部交互通过公开定义的接口进行。
2. **可部署：**构件自包含，可作为独立实体在目标平台运行，部署前无需重新编译。
3. **文档化：**使用者能根据文档判断构件是否满足要求。
4. **独立：**无需特殊构件即可组装部署；若依赖其他构件，应显式声明。
5. **标准化：**遵循某种构件模型。

### 从需求到系统的活动

来源给出的主要活动顺序为：系统需求概览 → 识别候选构件 → 根据发现的构件调整需求 → 架构设计 → 构件定制与适配 → 组装成系统。关键点是“发现构件后可能反过来调整需求”，因此复用选择会影响架构边界，而不是最后才处理的实现细节。

### 三种组装与接口匹配

- **顺序组装：**多个已有构件按顺序被调用，形成新的构件。
- **层次组装：**一个构件调用另一个构件；被调用方的提供接口要与调用方的请求接口兼容。
- **叠加组装：**两个或多个构件组合成新构件，对外提供新接口，原构件之间不互相依赖或调用。

三类兼容问题是：**参数不兼容**（参数类型或个数不同）、**操作不兼容**（操作名不同）、**操作不完备**（提供/请求接口的操作集合不完整匹配）。

```text
基于构件的软件开发
├─ 需求概览

├─ 发现构件后调整需求
├─ 架构设计

└─ 组装
   ├─ 顺序：依次调用
   ├─ 层次：请求接口 ↔ 提供接口
   └─ 叠加：组合能力，对外新接口
      └─ 检查参数 / 操作名 / 操作集合完备性
```

## 易混点 / 对比

- **层次组装 vs 叠加组装：**层次组装存在调用方与被调用方的接口匹配；叠加组装强调合并能力并对外提供新接口，原构件互不调用。
- **构件“独立”不等于没有依赖：**若服务依赖存在，来源要求显式声明。
- **适配不等于隐藏不兼容：**应识别参数、操作名或操作集合上的差异。

## 架构师视角

复用能减少重复构造，但构件的接口、依赖、标准与部署约束会影响系统结构。架构师需要将构件能力与需求边界对齐，判断是调整需求、适配构件还是不采用；仅比较功能清单不足以说明构件可组装。
